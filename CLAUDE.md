## Key standing rules, always apply:
- Never diagnose or interpret health data — show data, never a health judgment or recommendation
- No consumer-facing predictions or risk scores, ever — only the owner's own dog's real data/trends
- Free-text fields (notes, observations) must never flow into any B2B/licensing data export — structured scores only
- Always verify empirically before reporting something works (measure/query live state, don't just infer from a success message)
- Migrations: write the SQL file in `/migrations` (one-time schema changes, run once each), do NOT run it — John runs migrations manually in Supabase's SQL Editor. Reusable test-data tools (`delete_all_test_data.sql`, `verify_test_data_wiped.sql`) live separately in `/sql-utilities`, since they're repeatable data operations, not one-time schema changes.
- Before committing: show the diff for review first
- Before starting any local dev server for testing, check for and kill any existing node processes first (Get-Process node on Windows) — stray leftover servers from earlier sessions share the same live Supabase database as fresh test runs and can race against them, producing false-looking test failures (confirmed real occurrence: Aug 22, Stage 4 SMS-combining verification)
- **Never read `.env` (or any credential-bearing file) with `grep`, `cat`, `sed`, `head`, or `source` in a way whose output could include a matched line's value.** Checking whether a key exists must go through a real parser and print key names only — e.g. `node -e "console.log(Object.keys(require('dotenv').parse(require('fs').readFileSync('.env'))))"`. This applies even to "just checking structure" or "just checking one line" — the rule is about the command's output shape, not the intent behind running it. (Real incident: Aug 26, two separate leaks — see Build Log.)
- **Never use an unanchored/substring grep pattern against a secrets file.** Anchor to line start (`^KEY_NAME=`) and report presence/count only, not matched content — a short search term (e.g. `TZ`) can spuriously match inside a long base64/JSON blob.
- **Never `source` `.env` (or pipe it into any shell that interprets it) to debug a parse error.** If a line looks malformed, check its length or syntax validity as a boolean, or ask the user to look at that line directly — don't let bash's own error-reporting echo the raw line back.
- **When a secret's actual value is needed for a real check (an API call, an integration test), read it programmatically and use it in-process — never print it, echo it, or pass it as a literal string typed into a visible command.**
- **After any credential leak, escalate to a hard stop, not a soft resolution.** "I'll be more careful" is not a rule; "no further access to this file via shell text tools for the rest of the session, only via the dedicated non-printing check pattern" is.
- **Before running any command that touches a known-sensitive file, ask explicitly: does this command's default output include full matched content, not just whether something matched?** If uncertain, don't run it — construct the narrower version first.
- **If a leak happens anyway, stop and flag it explicitly and immediately as its own message** — never fold it into a later summary or continue working before surfacing it.
- **Before running any migration whose safety depends on a prior code deploy being live, verify the deploy actually completed via a real request to the live site — don't accept "confirmed working" without asking how it was confirmed.** (Real incident: Aug 26 RLS remediation — a code-change-then-migration sequencing gap was never independently verified, only taken on John's word; accepted as closed given low blast radius pre-beta, but the gap itself should have been checked, not assumed. See Build Log.)
- **When building or reviewing any JS-driven show/hide toggle (accordion, dropdown, menu), verify the click handler actually manipulates the exact attribute/class the CSS keys off — don't assume a toggle "looks wired up" from the markup alone.** (Real incidents: Aug 26 hamburger menu — JS toggled a `hidden` property the CSS never checked; Aug 28 FAQ accordion — no click handler existed at all despite complete markup/CSS. Same underlying risk, two different failure shapes, three days apart.)
- **`Public/assets/images/hero graphics/preview.html`'s `.cc-graphic` container must stay perfectly square (`aspect-ratio: 1/1`) at every viewport width — never a fixed `height` paired with `max-width`, which breaks the square at narrow widths and turns the circular photo crops into ovals.** A code comment directly above the rule carries this same warning; do not remove it or "simplify" it back to the broken combination. See the Build Log's Aug 31 entry and its "Hero Graphic — Photo Replacement" reference section for the full fix, the 5 photo slots' exact position/size values, and how to swap in a new photo without re-deriving anything.
